## 0011 报错根因（`column "id" of relation "backtest_trades" already has a default value`）
Django 的 PostgreSQL schema editor 执行 `AlterField(BacktestTrade, id)` 时会先
`ALTER COLUMN id DROP DEFAULT` 再重建，但只要该列**当前已有 default 且与目标
(BigAutoField/nextval) 相同**，这个 no-op 就会抛 `ObjectNotInPrerequisiteState`。

- **本机 Mac**：真实根因是序列漂移（seq=1,158,922,114，max(id)=1,158,922，id 曾被手工写入）。
  修复：`DROP DEFAULT` + `setval(max(id)+1)`（现 1158923）。之后 0011 正常通过。
- **远端 txy**：列本就是干净的 BigAutoField 形态（default=nextval，无漂移，
  seq 与 max(id) 一致=1,158,922），0011 的 AlterField 部分是纯 no-op 却仍报错。
  处理：跳过 AlterField，手动只执行 `AddField(cost_detail)` 并插入
  `django_migrations` 记录（脚本见 git 历史 / 已清理的 `tmp_migrate_0011.py`），
  然后 `migrate` 正常应用 0012–0014 及其余 app。

**建议**：`backtest/migrations/0011` 里的 `AlterField(backtesttrade, id)` 在「列已
处于目标形态」的生产库上是个陷阱。若未来要重放或新部署，可考虑把它拆成独立的
state-only 迁移（SeparateDatabaseAndState，不执行 DDL），避免 no-op 的 DROP DEFAULT。

## backtest_trades.id 的修复（仅本机 Mac 需要）
迁移 0011 需要 DROP DEFAULT，本机生产库序列漂移（seq=1,158,922,114，实际 max(id)=1,158,922，
即 id 曾被手工写入）。执行过：
```sql
ALTER TABLE backtest_trades ALTER COLUMN id DROP DEFAULT;
SELECT setval('backtest_trades_id_seq', max(id)+1, false);   -- 现为 1158923
-- （中间试过一次 ADD GENERATED ALWAYS AS IDENTITY，已 DROP IDENTITY 还原，无残留）
```
迁移后该列为 `bigint` + `DEFAULT nextval(...)`，与 Django BigAutoField 期望一致。
风险：若存在绕过 nextval 直接写固定 id 的路径，未来可能主键冲突；排查方向
`grep -rn "BacktestTrade(" backend/apps --include=*.py | grep -v tests` 的 update_or_create/objects.create。
